# greenpm 원장 엑셀 → Odoo 적재 스펙 설계 맵

> 상태: 살아있는 계약 (living spec) · 독자: 스펙 작성자 / 오케스트레이터
> 역할: 그린피엠(greenpm) 테넌트의 운영 원장 엑셀 1개를 Odoo 19 Enterprise의
> 판매·구매·재고·회계 데이터로 이관하는 작업을 독립 구현 가능한 단위로 분할한 최상위 설계도.
> 이 문서는 흐름(무엇이 어떤 순서로 무엇을 보장하는가)만 고정한다.
> 각 단위의 내부 구현은 구현 주체에 위임한다.
> 인간 검토면 = 이 맵의 흐름 + 각 단위 in/out·단언 + 의도적 검증 스킵 선언.

## 목적 / 의도

그린피엠은 매출·원부자재 매입·외주정산을 스프레드시트 한 장으로 관리해 왔다. 이 원장은
거래 사실의 유일한 기록이지만, 재고 잔량·미수금·손익을 사람이 눈으로 합산해야만 알 수 있고
문서(견적서·거래명세서·세금계산서)와 연결되어 있지 않다.

이 이관의 의도는 **원장에 적힌 거래 사실을 손실 없이 Odoo의 정규 거래 문서로 재현하는 것**이다.
재현이 끝나면 매출·매입·재고·미수금이 Odoo 표준 화면과 회계 보고서에서 그대로 조회되어야 하며,
합계는 원장과 원 단위까지 일치해야 한다.

**보존 원칙**: 원장의 날짜·금액·거래처는 원본 그대로 보존한다. 데모 목적의 날짜 이동이나
건수 증식은 이 계약의 범위가 아니다.

## 분할 원칙

- 한 단위의 in/out은 다른 단위의 내부를 몰라도 성립한다. 단위 간 주고받음은 접합부 계약이
  별도로 소유한다.
- 원본 엑셀은 **U1이 단독으로 읽는다.** 거래 적재 단위(U5·U6·U7)는 엑셀을 다시 파싱하지 않고
  U1이 낸 정규화 데이터셋만 소비한다. 이로써 파싱 규칙의 해석 차이가 단위마다 갈리는 것을 막는다.
- 기준정보 단위(U2·U3·U4)가 만들어 내는 **식별 문자열**(창고명·거래처명·품목명)은 거래 단위가
  조회 키로 쓴다. 어느 한 단위도 이 키 집합을 단독 소유하지 않으므로 별도 접합부 계약으로 분리한다.
- 각 작업 단위 스펙의 검증 단언 = 그 단위 작업 지시의 인수 게이트.

## 단위 트리

```
greenpm 원장 이관
│
├── U1  정규화 추출          원장 엑셀 → 정규화 데이터셋 3종 (+ 사용현황)
│                            └ 출력이 곧 접합부: 아래 U5·U6·U7의 유일한 입력
│
├── 기준정보 (거래 적재의 선행 조건, 서로 독립)
│   ├── U2  창고 재편        스토리지 2곳만 남는 창고 구조
│   ├── U3  거래처           고객 회사·담당자·공급업체
│   └── U4  품목             판매품·원자재·부자재·서비스
│
└── 거래 적재 (서로 독립, U1 + 기준정보에만 의존)
    ├── U5  매출            판매주문 → 배송 → 고객청구서 → 입금
    ├── U6  원부자재         공급업체청구서 → 입고 → 재고 실사
    └── U7  외주정산         공급업체청구서 → 지급

(횡단) S1  기준정보 식별 키 계약  ← U2·U3·U4가 생산, U5·U6·U7이 소비
```

**실행 순서 제약**: U1 → (U2·U3·U4 병렬) → (U5·U6·U7 병렬).
기준정보 3단위는 서로 독립이고, 거래 3단위도 서로 독립이다.

## U1 — 원장 엑셀을 결정론적 정규화 데이터셋으로 변환한다

- 입력: 원장 엑셀 1개 (시트 3장)
- 출력(계약): 매출 23 · 원부자재 15 · 외주 38 레코드의 정규화 데이터셋과, 합계가 원장과
  일치함을 보장. 소계행·서식행은 제거되고, 월만 적힌 시기는 확정 연월로 채워진다.
- 상태: 작업 단위 스펙 작성됨 ✅ → `u1-normalized-extract.md`

## U2 — 스토리지 2곳(고양·백석)에 대응하는 창고 구조만 남긴다

- 입력: 현재 테넌트의 창고 구조
- 출력(계약): 창고가 정확히 2개이며 각각 원장의 스토리지 값과 1:1 대응. 재고 이동 이력이
  없는 상태에서만 성립하는 구조 변경이다.
- 상태: 작업 단위 스펙 작성됨 ✅ → `u2-warehouse-realign.md`

## U3 — 원장에 등장하는 모든 거래 상대를 거래처로 확정한다

- 입력: 정규화 데이터셋의 거래처·담당자·매입처 컬럼
- 출력(계약): 고객 회사 17 · 고객 담당자 16 · 공급업체 18, 본지점 관계 1건.
- 상태: 작업 단위 스펙 작성됨 ✅ → `u3-partners.md`

## U4 — 원장에 실제로 등장하는 품목만 확정한다

- 입력: 정규화 데이터셋의 카테고리·구분 컬럼
- 출력(계약): 판매품 4 · 원자재 7 · 부자재 7 · 서비스 2. 원장에서 수량이 한 번도 발생하지
  않은 카테고리는 생성하지 않는다.
- 상태: 작업 단위 스펙 작성됨 ✅ → `u4-products.md`

## U5 — 매출 23건을 주문·배송·청구·입금까지 완결한다

- 입력: 정규화 매출 데이터셋 + S1 식별 키
- 출력(계약): 판매주문 23 · 주문라인 26 · 배송완료 23 · 게시된 고객청구서 23,
  공급가 4,864,178 + 세액 486,422 = 5,350,600, 미수금 1,430,000.
- 상태: 작업 단위 스펙 작성됨 ✅ → `u5-sales.md`

## U6 — 원부자재 매입을 전표·입고·현재고까지 완결한다

- 입력: 정규화 원부자재 데이터셋 + S1 식별 키
- 출력(계약): 게시된 공급업체청구서 10 + 초안 1, 게시분 합계 3,737,440,
  실사 후 현재고가 원장 잔여량과 일치.
- 상태: 작업 단위 스펙 작성됨 ✅ → `u6-materials.md`

## U7 — 외주·세무 비용을 전표와 지급까지 완결한다

- 입력: 정규화 외주 데이터셋 + S1 식별 키
- 출력(계약): 게시된 공급업체청구서 36, 합계 4,662,129, 미지급 0.
- 상태: 작업 단위 스펙 작성됨 ✅ → `u7-outsourcing.md`

## (횡단) 접합부 계약

- **S1 — 기준정보 식별 키**: U2·U3·U4가 생산하고 U5·U6·U7이 조회 키로 소비하는 문자열 집합
  (창고명 · 거래처명 · 품목명)이 무엇이어야 하는가. 거래 단위는 이 키로 조회했을 때 정확히
  1건이 나오는 것에만 의존하며, 기준정보가 어떻게 만들어졌는지는 알지 못한다.
  → `../_shared/greenpm-master-data-keys.md`
- **U1 출력 스키마**: U1이 단독 소유한다(자기 산출물의 출력 계약이므로 U1 스펙에 흡수).

## 전체 정합 단언 (단위 통합 후)

- **T1.** 고객청구서 합계(세금 포함) = 5,350,600
- **T2.** 공급업체청구서 합계(게시분, 세금 포함) = 3,737,440 + 4,662,129 = 8,399,569
- **T3.** 미수금 = 1,430,000, 미지급 = 0
- **T4.** 원장 어느 행도 누락되거나 중복되지 않음 — 매출 23 · 원부자재 15 · 외주 38
